공통 기반 ≠ 데이터 공개. 구성요소는 논리 계층으로 한 번씩 표시했습니다. 도메인별 CloudFront 배포·정책, 공개/사내 업무의 실행·권한은 구분합니다. CDN 캐시가 맞으면 앱·DB 호출 없이 콘텐츠를 전달합니다.

모든 서비스를 받치는 공통 기반

접속 단계가 아니라 개발·운영에 공통 적용

처음부터 크게 만들지 않고, 안전하게 확장합니다.

첫 제품은 인사평가입니다. 기존 시스템과 예산을 확인한 뒤 필요한 기반부터 구축하고, 외부 서비스는 업무와 보안 경계에 맞춰 순서대로 연결합니다.

01 / FIRST PRODUCT

인사평가를 끝까지 작동하게

인사담당자가 정리한 프로세스를 먼저 검토합니다. 평가 주기·대상·평가자·결과 공개 범위·수정 가능 시점을 합의하고, 작은 범위로 시험 운영합니다.

업무 확인→권한·데이터→시범 운영→확대
  • 직원·조직은 기존 HR 또는 그룹웨어를 원천으로 지정합니다.
  • 평가 기간의 조직·평가자 정보는 이력으로 보존해 조직 변경이 과거 평가를 바꾸지 않게 합니다.
  • 일정은 요구사항·연동·검증 범위를 확인한 후 산정합니다.
02 / DELIVERY

검증한 버전을 그대로 배포

GitHub Actions 등 회사의 Git 환경에 맞는 도구로 테스트·보안 검사·이미지 빌드를 연결합니다. 동일 이미지 digest를 ECR에서 승격하고, SSM 또는 CodeDeploy를 통한 EC2 배포와 되돌리기 절차를 기록합니다.

GitHub Actions→Test / Scan→ECR→SSM·CodeDeploy→EC2
  • 도구는 기존 Git 저장소와 보안정책을 확인한 뒤 확정하고, Production과 Non-production AWS 계정 분리를 검토합니다.
  • DEV → STAGE → 승인 → PROD 순서로 동일 Artifact를 승격하며 DB·파일·Secret·배포 권한은 환경별로 분리합니다.
  • Terraform으로 구성과 변경 이유를 관리합니다. DB 변경은 이전 버전 호환과 복구 가능성도 검증합니다.
03 / SECURITY & ACCESS

입구를 막고, 업무에서도 확인

국가 제한만으로 직원을 식별할 수 없습니다. 회사 IdP의 SSO·MFA로 인증하고, 애플리케이션에서 역할과 데이터 범위를 검사합니다.

  • 사내 화면과 people.starship-ent.com/api/*에 같은 국가·인증 정책을 적용합니다.
  • ALB 직접 주소를 통한 우회를 제한하고, 앱·DB는 Private 네트워크에 둡니다.
  • IAM Role 최소 권한, Secrets Manager, KMS, TLS와 개인정보가 노출되지 않는 감사 로그를 적용합니다.
  • 출장 예외는 승인된 VPN 또는 Zero Trust 경로와 IdP 정책을 함께 설계합니다.
04 / OPERATIONS & COST

초기 인력으로 감당할 범위부터

EC2·RDS를 기준으로 시작하되, 애플리케이션뿐 아니라 운영체제 패치·용량·장애·권한·비용·복구 책임도 함께 관리합니다. 담당자와 외부 지원 체계를 함께 정합니다.

  • CloudWatch로 오류·지연·EC2 인스턴스·DB 상태를 감지하고 담당자에게 알립니다.
  • EC2 이미지·설정 복구 절차와 RDS 자동 백업·PITR, 필요한 S3 Versioning·Lifecycle을 실제 복구 훈련으로 검증합니다.
  • RTO/RPO, 야간 대응, 대체 담당자, 유지보수 업체 역할을 합의합니다.
  • 트래픽·파일 용량·보존기간·가용성 목표를 기준으로 비용을 산정하고 Budgets와 태그로 추적합니다.
  • ALB·EC2·NAT 또는 Endpoint·DB·WAF·로그·전송료와 비운영 환경 비용도 포함합니다.
05 / MIGRATION

기존 업무를 유지하며 이전

시스템·서버·DB·연동·벤더·개인정보·백업 현황을 먼저 조사합니다. 그대로 옮길지, 일부만 바꿀지, 유지할지 시스템별로 결정합니다.

현황·의존성→시험 이전→대조·검증→전환→안정화
  • 건수·중요 필드·첨부파일 무결성, 권한과 주요 업무를 검증합니다.
  • 최종 동기화·중단 허용시간·실패 시 원복 기준을 전환 전에 정합니다.
  • 안정화와 승인 후 기존 시스템을 종료하고 임시 이전 데이터를 정리합니다.
06 / WEBSITE & FILES

홈페이지 성능은 먼저 측정

LCP, 이미지 크기, 캐시, API 응답과 JS 비용을 측정합니다. 이미지가 병목이면 크기·포맷·전달 경로부터 개선합니다.

원본 업로드→이미지 변환→S3→CloudFront
  • 필요 시 S3 이벤트·Lambda로 리사이즈와 WebP/AVIF 변환을 자동화합니다.
  • 화면 크기에 맞는 이미지를 보내고, 화면 밖 이미지를 지연 로딩합니다. 첫 핵심 이미지는 지연시키지 않습니다.
  • 오디션 영상은 홈페이지 공개 이미지와 분리합니다. 장시간 영상 처리는 Lambda로 단정하지 않습니다.

첫 설명 · 약 90초 · 말하는 속도에 따라 조절

“면접에서 말씀해주신 인사평가시스템과 클라우드 이전을 기준으로, 제가 어떤 순서로 접근할지 정리해봤습니다. 내부 환경은 아직 모르기 때문에 검토용 구조입니다.”

“위쪽은 이용자입니다. 팬은 공개 콘텐츠를 보고, 지원자는 개인정보와 영상을 제출하며, 임직원은 평가 업무를 합니다. 같은 기반을 활용하되 들어오는 경로와 데이터 권한은 구분했습니다.”

“먼저 인사평가를 만들겠습니다. 직원은 사내 계정으로 인증하고, 본인·평가자·인사담당자에게 허용된 내용만 봅니다. 앱과 데이터베이스에는 인터넷에서 직접 접근하지 못하게 하고, 첨부파일은 별도 저장소에서 권한을 확인해 제공합니다.”

“혼자 운영할 가능성을 고려해 관리형 서비스를 우선 검토했습니다. 배포 전 검증, 장애 알림, 백업과 실제 복구 절차를 함께 갖추겠습니다. 이후 홈페이지나 오디션에도 이 기준과 공통 기능을 재사용하겠습니다.”

“입사 후에는 기존 환경·업무·예산과 복구 목표를 확인하고, 첫 범위와 일정을 인사·보안 담당자와 합의하겠습니다.”

이어질 질문에 답하는 기준

AWS를 회사에서 직접 구축해보셨나요?

“회사에서는 Docker 기반 서버 배포와 Jenkins 연동 경험이 있고, AWS는 개인 프로젝트에서 사용했습니다. 이 자료는 그 경험을 바탕으로 조직 운영에 필요한 요소를 검토한 안입니다. 조직 차원의 계정·권한·네트워크는 내부 정책과 기존 담당자·협력사 구성을 확인하며 검증하겠습니다.” 실제 수행 범위에 맞춰 설명하고 이 설계안을 운영 실적으로 표현하지 않습니다.

왜 EC2와 RDS인가요?

“채용공고에 명시된 AWS 운영 범위와 기존 서버 이전 가능성을 고려해 EC2를 기본안으로 표현했습니다. 애플리케이션은 Docker로 배포하고 DB는 RDS를 사용해 데이터베이스 운영 부담을 줄이는 방향입니다. 실제 구성은 기존 서버·트래픽·가용성·운영 지원 범위를 확인한 뒤 인스턴스 수와 배포 방식을 확정하겠습니다.”

비용과 개발 기간은 얼마나 드나요?

“사용 인원, 평가 프로세스, 연동 범위, 파일 용량과 가용성 목표를 확인해야 산정할 수 있습니다. 먼저 핵심 업무 범위를 합의하고 개발·검증·이전·운영 비용을 나눠 제시하겠습니다.” 근거 없는 월 비용이나 완료 날짜를 약속하지 않습니다.

혼자서 이 전체를 만들 수 있나요?

“처음부터 전체를 동시에 만들 계획은 아닙니다. 인사평가와 그 운영에 필요한 최소 기반부터 진행합니다. 기존 SSO·그룹웨어·SaaS를 재사용하고, 네트워크·이전·장애 대응에서 외부 지원이 필요한 범위도 함께 정하겠습니다.”

해외 출장 중이면 업무를 못 하나요?

“국내 접근을 기본으로 검토하되 출장 업무는 사전에 확인하겠습니다. 승인된 VPN 또는 Zero Trust 접근과 MFA를 연결해 예외 경로를 마련합니다. 국가 차단 자체를 직원 인증 수단으로 보지는 않습니다.”

기존 시스템은 전부 새로 개발하나요?

“현황과 의존성을 먼저 보고 그대로 이전, 일부 개선, 유지, 종료를 나누겠습니다. 업무가 끊기지 않게 시험 이전과 데이터 대조, 원복 기준을 준비하고 승인 후 전환하겠습니다.”

이 자료에서 가장 강조하고 싶은 건 무엇인가요?

“첫 제품의 기능 구현과 운영을 함께 생각했다는 점입니다. 인사평가를 안전하게 오픈하고, 그 과정에서 만든 권한·배포·모니터링·UI 기준을 다음 시스템에도 활용하겠습니다.”
